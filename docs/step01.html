骨架與 drone API 基線

這一步只做兩件事：讓 repo 裝得起來、跑得起來、測得起來；然後繞過本後端，直接量 drone 自己， 把它今天的行為——欄位、時間單位、起飛與降落要多久——存成 docs/baseline.md。 後面每一個 step 都拿這份數字當對照組：沒有它，「我沒弄壞」就只是一句話。

本 repo 的腳本與測試（bash／pytest） drone 的 coordinator（HTTP :7070） 飛控（ArduPlane SITL：電腦上模擬的飛控與機體） 本後端 marine-backend-py（:8100；本章只有 /health，step 2 起才接上 drone）

為什麼需要這一步

這個專案要做的是一條很短的鏈：瀏覽器 → 本後端（:8100）→ 每台 drone 的 coordinator（:7070）→ 飛控。 step 2、step 3 會在中間那一段寫程式，而驗收標準寫的是「按了起飛，drone 真的飛到 10 m」。 問題是：10 m 要飛多久才算正常？降落 20 秒是快還是慢？update_time 是秒還是毫秒？ 這些都不是本後端決定的，是 drone 決定的——所以要在本後端還不存在的時候，先直接量 drone。

直接量還有第二個理由：之後經由後端量到的數字，只要和這裡的數字差不多，就能說「後端沒有拖慢或弄壞什麼」； 差很多，就知道問題出在後端那一段。這就是 ROADMAP 工作流程規則 7 說的基線對照。

本章會用到的飛控名詞（沒碰過 ArduPilot 的話先看這裡）
  • SITL：在電腦上模擬的飛控與機體，跑在 docker 容器裡。本章說「會真的飛」，指的是模擬機在模擬器裡真的起降，不是實機。
  • ArduPlane quadplane：ArduPilot 的固定翼韌體加上垂直起降（VTOL）旋翼。本專案只用它的多旋翼飛法，名字 Q 開頭的模式（QLAND、QRTL…）就是這一類。
  • arm／disarm：解鎖／上鎖馬達。armed 表示馬達可以出力，不論在地面或空中；飛控偵測到著地後會自動 disarm。
  • pre-arm：飛控在允許 arm 之前做的自我檢查。is_ready_to_arm 就是它的結果。
  • flight_mode 是整數（ArduPlane 的 custom mode，對照表取自 pymavlink 的 mode_mapping_apm）。本章出現的： 15 GUIDED（聽外部指令飛，起飛就用它）、20 QLAND（原地垂直降落）、21 QRTL（垂直返航並降落）、11 RTL（返航）。
  • MAVLink：飛控對外溝通的協定。圖裡的 DO_SET_MODE、NAV_TAKEOFF 是它的指令名，ACK 是飛控的回覆。
  • GCS（地面站）：任何能對飛控下指令的程式。本後端也算一個，所以同一台 drone 同時只該有一個 GCS 在下指令。
  • marlin-drone：drone 端的 repo，coordinator 的原始碼在裡面；本章引用的 drone_api_server.py 等檔案都在那裡。
  • 「規則 N」「選型決策 N」「G 編號」都在 repo 根目錄的 ROADMAP.md：規則是「工作流程規則」，G1–G10 是「對 drone 側介面的審查」裡列的缺口（例如 G2＝兩個時間欄位單位不同、G6＝takeoff 回 200 只代表已派發）。

起飛前要先按 arm，或先手動切到 GUIDED 不用。POST /api/takeoff 自己會切 GUIDED 並 arm；腳本在 is_ready_to_arm 不是 true 時也會自己先切 GUIDED（preflight()）。

全景：一次基線 run 的完整旅程

腳本一次 run 做的事，按時間順序畫出來就是下面這張圖。三條直線是三個執行者：左邊是我們的腳本， 中間是 drone 容器裡的 coordinator（它把 HTTP 翻成 MAVLink），右邊是飛控。 點圖上的方框可以跳到講那一段的小節。

基線腳本：直接量 drone

scripts/baseline_drone_direct.sh <drone_url> 是這一步的主角。它只用 curl 和 jq， 對 drone 做三件事：記下版本與欄位、確認可以起飛、然後起降三次並計時。 它的 stdout 只印要貼進 docs/baseline.md 的那幾行（VERSION、FIELDS、UNITS、RUN、MEDIAN）， 進度一律印到 stderr，這樣輸出本身就是可被測試斷言的契約。 

set -euo pipefail

DRONE=${1:?usage: $0 <drone_url>}
DRONE=${DRONE%/}
RUNS=${RUNS:-3}
ALTITUDE=${ALTITUDE:-10}
ALT_REACHED=${ALT_REACHED:-9.5}
POLL_S=${POLL_S:-0.5}
READY_TIMEOUT_S=${READY_TIMEOUT_S:-10}
TAKEOFF_TIMEOUT_S=${TAKEOFF_TIMEOUT_S:-120}  # the drone's own DroneParams.TAKEOFF_TIMEOUT
LAND_TIMEOUT_S=${LAND_TIMEOUT_S:-180}

set -euo pipefail 讓腳本在任何指令失敗、用到未定義變數、或管線中任一段失敗時立刻結束。 ${X:-預設} 是「環境變數 X 沒設就用預設」，所以每個參數都能從外面覆寫，測試就是靠這個把逾時縮短。 停錶門檻 ALT_REACHED=9.5 來自 ROADMAP 的驗收標準（alt_rel ≥ 9.5，比目標 10 m 低 0.5 m）； alt_rel 是離 home（起飛點）的高度，單位公尺。

所有 HTTP 都走同一個 req

# req METHOD PATH [BODY] [TIMEOUT]  ->  sets CODE and BODY. Never call it in $(…):
# its die must exit the script, not a subshell.
req() {
  local method=$1 path=$2 body=${3:-} timeout=${4:-5} rc=0
  local args=(-sS -m "$timeout" -o "$TMP/body" -w '%{http_code}' -X "$method")
  [[ -n $body ]] && args+=(-H 'content-type: application/json' -d "$body")
  CODE=$(curl "${args[@]}" "$DRONE$path" 2>"$TMP/err") || rc=$?
  ((rc == 0)) || die "drone unreachable: $method $path: $(cat "$TMP/err")"
  BODY=$(cat "$TMP/body")
}

兩個設計點。第一，每個請求都有 -m 逾時，所以腳本不可能卡死在網路上（工作流程規則 6）。 第二，req 把結果寫進全域變數 CODE／BODY，而不是 echo 出來讓呼叫端用 $(req …) 接。 原因在註解裡：$(…) 是子 shell，裡面的 die 只會結束那個子 shell， 腳本本體會拿著空字串繼續往下跑——失敗被吞掉了。

幾個 bash 語法，讀不慣的話：

  • ${3:-}：第 3 個參數，沒給就是空字串（在 set -u 下直接寫 $3 會報錯）。
  • args=(…) 是陣列，"${args[@]}" 把它逐項展開成 curl 的參數，含空白的項也不會被拆開。
  • … || rc=$?：curl 失敗時把結束碼存進 rc，而不是讓 set -e 直接結束腳本，這樣才能印出像樣的錯誤訊息。
  • -w '%{http_code}' 讓 curl 把狀態碼印到 stdout（回應本文寫進 -o 指定的檔案）；$TMP 是腳本開頭 mktemp -d 建的暫存目錄。
  • 腳本裡其他小工具：read_state 把 /get_drone_state 讀進 STATE、field X 用 jq 取欄位、 now 是含小數的秒、is_true 與 calc 用 awk 做浮點比較和運算（bash 只會整數）。

前置條件：is_ready_to_arm 跟著模式走

ROADMAP 對前置條件的要求是「is_ready_to_arm == true，否則大聲失敗」。 第一次實際讀 drone-1（第一台模擬 drone，位址 172.18.10.2:7070，查法見〈對 SITL 跑基線〉），它是 false，模式 21（QRTL）； gps_fix_type 6（RTK fixed，比一般 3D 定位的 3 還好）、10 顆衛星，看起來什麼都沒壞。 原本以為這代表飛機有問題、起飛會被拒絕。追下去才發現：

  • is_ready_to_arm 不是 coordinator 自己算的，是飛控自己的 pre-arm 位元 （SYS_STATUS 的 MAV_SYS_STATUS_PREARM_CHECK，見 marlin-drone drone/mavlink_telemetry_consumer.py）。
  • ArduPlane 4.6.3 的 pre-arm 會問「目前的模式能不能 arm」。ModeQLand、ModeQRTL、ModeRTL 的 _pre_arm_checks 直接 return false（ArduPlane/mode.h），ModeGuided 是 return true。
  • 而我們自己的降落就停在 QLAND。也就是說每一輪降落完，is_ready_to_arm 一定是 false。
  • 但 POST /api/takeoff 會先切 GUIDED 再 arm，所以照樣起飛：coordinator 的 log 裡， 2026-09-24 06:06:13 剛 disarm，06:06:14 就 ARM: ACCEPTED。
  • 這也推翻了 ROADMAP step 3 的一條驗收：它原本打算拿「剛降落完、is_ready_to_arm=false 時按起飛」當 drone 會拒絕的例子。 那個前提不成立，已經記進 ROADMAP，step 3 要另找會被拒絕的情境。

當時有三個選擇：把這幾個模式視為可接受、完全不檢查而交給 takeoff 自己拒絕（drone 拒絕指令時回 409，飛控沒回應時回 504）、或維持原規則。 最後維持原規則（ROADMAP 選型決策 7）：腳本先用 coordinator 的 POST /api/set-mode 把飛機放進 GUIDED， 實測 1 秒內 is_ready_to_arm 變成 true，然後才嚴格檢查。已經 armed 的飛機一律不碰——那代表別人正在飛它。 

preflight() {
  read_state
  if [[ $(field is_armed) == true ]]; then
    die "PRECONDITION FAILED: is_armed=true flight_mode=$(field flight_mode) — something else is flying it; not touching it"
  fi
  if [[ $(field is_ready_to_arm) != true ]]; then
    log "is_ready_to_arm=false in flight_mode=$(field flight_mode); switching to GUIDED"
    req POST /api/set-mode '{"mode":"GUIDED"}' 15
    [[ $CODE == 200 ]] || die "POST /api/set-mode GUIDED -> HTTP $CODE $BODY"
    local t0
    t0=$(now)
    while read_state && [[ $(field is_ready_to_arm) != true ]]; do
      is_true "$(now) - $t0 < $READY_TIMEOUT_S" || break
      sleep "$POLL_S"
    done
  fi
  if [[ $(field is_ready_to_arm) != true ]]; then
    die "PRECONDITION FAILED: is_ready_to_arm=false flight_mode=$(field flight_mode) gps_fix_type=$(field gps_fix_type)"
  fi
}

時間欄位的單位（G2）

/get_drone_state 有兩個時間欄位：update_time（最後一次收到 MAVLink 的時間）和 timestamp（這個回應產生的時間）。 規劃時實測就懷疑兩者單位不同。腳本不照抄假設，而是拿主機時間去比，自己判斷： 

unit_of() {  # value now -> s | ms | unknown
  awk -v v="$1" -v n="$2" 'function abs(x) { return x < 0 ? -x : x }
    BEGIN { if (abs(v - n) < 86400) print "s"; else if (abs(v / 1000 - n) < 86400) print "ms"; else print "unknown" }'
}

判斷方式：和主機現在的秒數相差不到 86400（一天的秒數）就是秒，除以 1000 之後才接近就是毫秒。 結果是 UNITS update_time=s timestamp=ms。step 2 算 telemetry_age_s 時只能用 update_time， 拿錯欄位會差 1000 倍，斷線的 drone 看起來還活著。

中途失敗也要把飛機降下來

cleanup() {
  local rc=$?
  trap - EXIT
  if ((COMMANDED)); then
    # An abort between takeoff and touchdown must not leave the aircraft flying.
    if curl -sS -m 5 "$DRONE/get_drone_state" 2>/dev/null | jq -e '.is_armed == true' >/dev/null 2>&1; then
      log "aborting with the aircraft armed: sending POST /api/land"
      curl -sS -m 30 -X POST -H 'content-type: application/json' -d '{}' "$DRONE/api/land" >&2 || true
      echo >&2
    fi
  fi
  rm -rf "$TMP"
  exit "$rc"
}
trap cleanup EXIT
trap 'exit 130' INT TERM

die 就是 exit 1，所以任何失敗（逾時、連不上、被拒絕）都會走到這個 EXIT trap。 它不看腳本「以為」飛機在哪個狀態，而是再問一次 drone：只要還 armed 就送 land。 Ctrl-C（INT）和 kill 預設送的 TERM 也一樣，被轉成 exit 130（慣例是 128＋訊號編號，INT 是 2），照樣觸發 EXIT trap。 trap - EXIT 是先把自己拆掉，免得 cleanup 最後的 exit 又觸發一次 cleanup； jq -e 讓 jq 的結束碼跟著運算結果走（true 為 0），if 就能直接拿它判斷。

腳本也要先寫測試：假 drone 與結束碼契約

工作流程規則 8 說單元測試不碰 SITL，規則 10 說先寫測試。那一支會真的讓飛機起飛的腳本要怎麼測？ 做法是在 localhost 起一個假 coordinator（tests/fake_drone.py，只用標準庫的 http.server）， 它的回應形狀照 marlin-drone 的 drone_api_server.py 抄：takeoff 回 {"task_id", "message"}、 被拒時回 {"detail": …}、update_time 秒、timestamp 毫秒。 最重要的是它模擬了上面那個坑： 

            ready = self.flight_mode == GUIDED and self.ready_after_guided
            …
                "is_ready_to_arm": ready or self.is_armed,

or self.is_armed 也是照真的飛控抄的：飛機 armed 之後，ArduPilot 一律回報 pre-arm 健康， 所以整段飛行中 is_ready_to_arm 都是 true（coordinator 原始碼的註解寫明這是旗標本身的語意）。

然後用 subprocess 真的去跑腳本，斷言它的結束碼、印出來的字、以及它送了哪些請求。 測試的來源是規格（ROADMAP 的要求與 drone 的原始碼），不是腳本本身。例如「不 ready 就大聲失敗，而且根本不送 takeoff」：

收尾不留殘留：smoke_health.sh

「scripts/dev.sh 之後 curl localhost:8100/health」這條驗收如果用手打，就是一次性的； 依工作流程規則 5 把它寫成腳本：起後端、打 /health、收掉整個 process group、證明沒有 uvicorn 留下。 這裡連踩兩個坑，修法都在腳本本體： 

# Match on the process name (-x), then filter its arguments. `pgrep -f <pattern>` matches
# any command line containing the pattern -- including the shell that typed it.
leftovers() {
  { pgrep -ax uvicorn; pgrep -ax uv; } | grep -F "marine_backend.main:app --port $PORT" || true
}
…
# The inner bash records its own pid before exec'ing, and that pid is the session and
# group leader. ($! is not reliable: when the calling shell has job control on (set -m),
# a background job gets its own process group, so setsid is already a group leader and
# forks and exits -- $! then names a dead process.)
setsid bash -c 'echo $$ >"$1"; exec scripts/dev.sh' _ "$LOG.pid" >"$LOG" 2>&1 </dev/null &
timeout 5 bash -c "until [[ -s '$LOG.pid' ]]; do sleep 0.05; done"
PGID=$(cat "$LOG.pid")

先講為什麼要收「整個 process group」。dev.sh 最後一行是 exec uv run uvicorn …：exec 用新程式取代目前的 shell， pid 不變；但 uv run 會再生出真正跑 uvicorn 的 Python 子程序，--reload 還會再多一層。 只殺最上面那個 pid，底下的子程序可能活下來。process group 是一組一起收訊號的行程； setsid 讓它後面的程式自成一個新的 session 與 group（group id＝它自己的 pid）， 之後 kill -- -$PGID（pid 前面加負號）就是把訊號送給整組。 bash -c '…' _ "$LOG.pid" 裡的 _ 只是佔住 $0 的位置，讓後面的檔名成為 $1；$$ 是那個 bash 自己的 pid。

第一個坑：原本以為 setsid cmd & 之後的 $!（最後一個背景程序的 pid）就是新 group 的 leader。 實際上，當呼叫端的 shell 開著 job control（set -m，互動 shell 通常是）時，每個背景 job 都會自成一個 group， 於是被丟到背景的 setsid 自己已經是 group leader；setsid 這時會 fork 一份再自己退出—— $! 指向一個死掉的 PID，kill -- -$PGID 拿到空字串，uvicorn 留在背景繼續佔著 8100。 沒有 job control（set +m，一般腳本的預設）時 $! 其實是對的；兩種情況都實測過。 讓內層 bash 自己把 pid 寫進檔案，兩種情況都成立。 （這一段的成因，第一版寫成「非互動 shell 才會這樣」，剛好寫反了，是冷讀抓到的。） 第二個坑：用 pgrep -f "uvicorn marine_backend" 檢查殘留，會比對到下這條 pgrep 的那個 shell 自己的命令列， 於是明明乾淨也回報有殘留。

三輪結果與回歸容差

常見錯誤

把 is_ready_to_arm=false 當成「不能飛」

症狀
剛降落完的 drone 永遠顯示 not ready。
後果
前置檢查擋掉一台其實能飛的飛機；或 UI 把起飛按鈕灰掉。
正解
它是飛控的 pre-arm 位元，QLAND／QRTL／RTL 下必定 false。先切 GUIDED 再看。

把 takeoff 的 200 當成「飛到了」

症狀
POST 0.03 s 就回 200，飛機才剛離地。
後果
計時從回應算起、或以回應為準宣告完成，數字與事實都錯（G6）。
正解
碼錶停在 drone 自己回報的 alt_rel ≥ 9.5。

拿 timestamp 算遙測新鮮度

症狀
斷線的 drone 看起來一直很新鮮，或新鮮的看起來過期很久。
後果
毫秒當秒用，差 1000 倍（G2）。
正解
只用 update_time（秒）；timestamp 是回應產生的時間，而且是毫秒。

ROS 的 PYTHONPATH 漏進 venv

症狀
uv run pytest 在收集之前就 ModuleNotFoundError: No module named 'yaml'，traceback 指向 /opt/ros/humble。
後果
一條測試都跑不了，而且看起來像是自己的程式壞了。
正解
addopts = "--disable-plugin-autoload"；會跑 Python 的腳本先 unset PYTHONPATH。

在 $(…) 裡呼叫會 die 的函式

症狀
請求失敗了，腳本卻拿著空字串繼續跑。
後果
失敗被吞掉，之後的錯誤訊息指向完全不相干的地方。
正解
讓函式寫全域變數（CODE／BODY），在主 shell 呼叫。

setsid cmd & 後用 $! 收程序

症狀
kill: -: arguments must be process or job IDs，8100 依然被佔。
後果
uvicorn 殘留在背景，下一次啟動撞 port。
正解
讓內層 bash 先把自己的 pid（＝group id）寫進檔案再 exec。

用 pgrep -f 查殘留

症狀
明明收乾淨了，檢查卻說還有殘留。
後果
要嘛誤判失敗，要嘛久了大家學會忽略這個檢查。
正解
比對行程名稱（pgrep -ax uvicorn）再過濾參數，或把樣式錨定在開頭（^bash scripts/…）。

測試只因「檔案不存在」紅過

症狀
先寫測試、看它紅、寫實作、看它綠——每一步都做了。
後果
不知道哪一條測試其實什麼都沒守住。
正解
對實作的副本逐一拿掉行為（mutation），確認每一條都有自己會紅的時候。

  • drone 今天的行為存證在 docs/baseline.md：版本 1.8.4、45 個欄位、update_time 秒／timestamp 毫秒、起飛 5.28 s、降落 22.97 s。

自我測驗

1. drone 剛降落完，is_ready_to_arm=false。這時送 POST /api/takeoff 會怎樣？為什麼？

會起飛。降落把飛機留在 QLAND，而 ArduPlane 的 QLAND 在 pre-arm 階段一律回「mode not armable」，所以這個位元是 false； 但 takeoff 會先切 GUIDED（pre-arm 通過）再 arm。false 反映的是「目前的模式」，不是飛機的健康。

2. takeoff_s 從哪一刻算到哪一刻？為什麼不在 takeoff 回 200 時停錶？

從送出 POST 前一刻，到 drone 自己的 /get_drone_state 報出 alt_rel ≥ 9.5。200 只代表派發成功（G6），實測 0.03 s 就回，那時飛機才剛開始爬升。

3. 如果把 req 改成 echo "$BODY"，呼叫端寫 STATE=$(req GET /get_drone_state)，drone 連不上時會發生什麼？

die 在 $(…) 的子 shell 裡執行，只結束子 shell；主腳本拿到空的 STATE 繼續跑，錯誤訊息會出現在後面不相干的 jq 那一行。（嚴格說，set -e 下賦值會帶著子 shell 的結束碼，腳本也可能在那裡停住，但訊息已經被吞掉了。）

4. 為什麼 8 條腳本測試都紅過了，還要做 mutation？

它們第一次紅都是因為腳本不存在（exit 127）。那只證明「沒有腳本時會紅」，不證明每一條守得住它宣稱的那個行為。mutation 一次拿掉一個行為，才看得出每條測試各自會在什麼時候紅。

5. 你跑出來的起飛時間是 6.9 s，基線中位數是 5.28 s。算不算回歸？

不算。規則 7 的容差取「±30%（±1.58 s）」與「±5 s」較寬者，也就是 ±5 s，範圍 0.28–10.28 s；而且規則 7 看的是 3 次的中位數，不是單次。
